# Экспериментальные серии

Эксперимент разворачивает одну конфигурацию в матрицу «брокер × значение переменной × повторение». Каждый элемент выполняется существующим оркестратором как отдельный сценарий со свежими контейнерами и сетью. Пример `examples/producer-scaling.json` содержит 64 прогона; 1000 RPS относится к каждому producer, поэтому суммарная целевая нагрузка растёт вместе с их числом.

## Запуск

```sh
MAX_CONCURRENT_SCENARIOS=1 docker compose up --build -d orchestrator prometheus grafana
python -m src.cli experiments plan --file examples/producer-scaling.json
python -m src.cli experiments run --file examples/producer-scaling.json
python -m src.cli experiments status EXPERIMENT_ID
python -m src.cli experiments results EXPERIMENT_ID
```

CLI обращается к API, по умолчанию `http://localhost:8080`. Для другого адреса укажите `experiments --api-url URL` перед командой. Запуск CLI внутри Compose: `docker compose run --rm benchmark-cli experiments --api-url http://orchestrator:8080 plan --file examples/producer-scaling.json`.

`MAX_CONCURRENT_SCENARIOS` — общий лимит серий и одиночных сценариев, по умолчанию 1. Слот занят с начала подготовки контейнеров до завершения финального сбора и очистки. Число слотов не является оценкой достаточности CPU/RAM: при увеличении лимита сценарии конкурируют за ресурсы одного хоста. Лимит и фактические пересечения сохраняются в результатах.

## Типы и переменные

| Тип | Исследуемая переменная | Модель |
|---|---|---|
| `producer_scaling` | `values` заменяют `producer.count` | `work_queue` |
| `consumer_scaling` | `values` заменяют `consumer.count` | `work_queue` |
| `message_size` | `values` заменяют `producer.payload_size`, в КиБ | `work_queue` |
| `pub_sub` | `values` заменяют `consumer.count` | `pub_sub` |
| `load_ramp` | Один линейный профиль внутри каждого прогона | `work_queue` |

Для первых четырёх типов задайте постоянную нагрузку и уникальные положительные целые `values`. Для `load_ramp` удалите `values` и добавьте:

```json
"ramp": {
  "start_rps": 100,
  "end_rps": 1000,
  "step_duration_seconds": 20
}
```

Продолжительность измерения должна делиться на длительность ступени и содержать минимум две ступени. Начальный и конечный RPS входят в профиль. Параметры `ramp` заменяют параметры нагрузки шаблона. Для других типов изменяется только исследуемое поле. Модель взаимодействия должна соответствовать типу; ошибочная конфигурация отклоняется целиком до создания ресурсов.

Сценарии гарантий с персистентностью и скачкообразной нагрузкой пока не поддерживаются. Kafka `work_queue` допускает до 16 consumers. NATS Pull использует обязательный AckExplicit, в том числе при выбранном минимальном режиме: это различие нативных механизмов следует учитывать в выводах.

## API

| Метод | Путь | Действие |
|---|---|---|
| POST | `/api/v1/experiments/plan` | Проверить спецификацию, получить полный план без запуска |
| POST | `/api/v1/experiments` | Создать и запустить серию |
| GET | `/api/v1/experiments` | Список серий |
| GET | `/api/v1/experiments/{id}` | Состояние, прогоны, попытки и ошибки |
| POST | `/api/v1/experiments/{id}/cancel` | Отменить ожидающие и активные прогоны серии |
| POST | `/api/v1/experiments/{id}/resume` | Возобновить прерванные и отменённые прогоны |
| POST | `/api/v1/experiments/{id}/retry-failed` | Явно создать новые попытки ошибочных прогонов |
| POST | `/api/v1/experiments/{id}/analyze` | Пересчитать статистику завершённой серии |
| GET | `/api/v1/experiments/{id}/results` | Сводка и попарные сравнения |

Соответствующие команды CLI: `cancel`, `resume`, `retry-failed`; удалённый пересчёт — `analyze --experiment-id ID`. Ошибка прогона не вызывает автоматический повтор. `retry-failed` также позволяет явно повторить прогоны с технически неполными метриками, перечисленными в `invalid_metrics`. Старые попытки остаются в прогрессе, но в анализ попадает последняя попытка каждого повторения.

## Сохранение и восстановление

`BENCHMARK_RESULTS_DIR` задаёт каталог результатов, по умолчанию `/app/results` в контейнере. Для локального сервиса задайте доступный каталог явно. Серии хранятся в `experiments/<id>/`: `specification.json`, неизменяемый `plan.json`, `progress.json`, копии результатов в `runs/`, а также производные `summary.json`, `comparisons.json`, `runs.csv`.

Изменяемые JSON записываются атомарно с fsync. Каталог принадлежит одному управляющему процессу; блокировка не позволяет двум экземплярам сервиса одновременно управлять сериями. После рестарта активные попытки становятся прерванными. Уже записанный успешный результат восстанавливается без повторного запуска. Для продолжения нужна явная команда `resume`; она очищает остатки ресурсов прерванных попыток. Завершённые прогоны повторно не запускаются.

Офлайн-пересчёт не требует работающих Docker, API и Prometheus:

```sh
python -m src.cli experiments analyze --directory results/experiments/EXPERIMENT_ID
```

Сначала дождитесь завершения серии; не запускайте офлайн-запись параллельно её выполнению.

## Измерения и качество

Все адаптеры ожидают готовность клиентов и общий момент начала фаз. Счётчики сообщений и полезных байтов для RPS фиксируются отдельным таймером на границе измерения, без дополнительной операции на каждое сообщение. Задержка выполнения таймера сохраняется; при задержке больше 0.1 секунды скорости исключаются из статистического сравнения. Финальные счётчики измерительных сообщений включают доставки в drain, а скорости — только счётчики на границе измерения. `late_deliveries` отражает разницу между финальным приёмом и приёмом на границе измерения.

Общая задержка относится к сообщениям измерительной фазы, включая доставленные в drain. Для возрастающей нагрузки счётчики и гистограмма дополнительно фиксируются на границах ступеней отдельным таймером. Это даёт RPS, среднюю задержку и перцентили каждого интервала без расчёта номера ступени на каждом сообщении. Задержка сообщения, дошедшего в следующей ступени, относится к интервалу его получения.

Ресурсы получаются из Prometheus только внутри временных границ измерения и ограничены разрешением scrape 5 секунд. CPU хранится в использованных ядрах, RAM — в байтах. Для каждой роли сначала суммируются ряды её контейнеров, затем вычисляются среднее и максимум. Интервалы короче scrape и интервалы без достаточных данных дают отсутствующие показатели.

Прежде чем удалить клиентов, сервис дожидается финальных метрик каждого экземпляра. Неподтверждённый финальный сбор исключает прогон из анализа; отдельные отсутствующие метрики исключаются по отдельности. Нули не подставляются. Для RabbitMQ work queue дополнительно проверяется очередь; для остальных вариантов отсутствие сообщений не объявляется доказанной потерей, если учёт доставки не завершён. Недостигнутый целевой RPS сохраняется как наблюдаемый результат с предупреждением.

## Статистика

Независимое наблюдение — один прогон. Группы формируются отдельно для каждого значения переменной и брокера. Итог включает mean, median, Q1, Q3, IQR, число наблюдений и причины исключений. 95% percentile bootstrap-интервалы среднего, медианы и δ Клиффа используют 10 000 перевыборок и воспроизводимый seed. Это индивидуальные интервалы, без коррекции одновременного покрытия.

Каждая пара брокеров сравнивается при одинаковом значении переменной двусторонним тестом Манна–Уитни. При отсутствии связок и минимальном размере группы ≤8 используется точный метод, иначе — асимптотический с учётом связок. Реализация опирается на [документацию SciPy](https://docs.scipy.org/doc/scipy/reference/generated/scipy.stats.mannwhitneyu.html). Семейство поправки Холма объединяет все сравнения одной метрики в серии, включая все значения переменной; alpha = 0.05.

δ Клиффа определяется как P(A>B)−P(A<B): положительный знак означает большие численные значения у A, а не автоматически лучший результат. Для задержки меньше обычно лучше, для throughput — больше. Категории по |δ|: <0.147 negligible, <0.33 small, <0.474 medium, иначе large.

При одном наблюдении интервалы не строятся; при числе наблюдений менее пяти отмечается малая выборка. Для теста необходимы хотя бы два валидных прогона в каждой группе. Идентичные константные выборки дают p=1 и δ=0. Тест не следует интерпретировать как универсальную проверку равенства медиан: он сравнивает распределения независимых наблюдений.

Метрики наблюдаемости серий: `benchmark_experiment_status`, `benchmark_experiment_runs`, `benchmark_orchestrator_scenario_slots`; занятость отражает `benchmark_orchestrator_active_scenario_tasks`.

## Grafana при масштабировании

На дашборде `Scenario producers and consumers` выберите `Scenario`, затем оставьте `Containers = All`, чтобы видеть всех producers и consumers. На графиках RPS, числа сообщений, ошибок, in-flight, CPU и RAM отображаются отдельные экземпляры и толстая пунктирная линия `TOTAL selected`. CPU/RAM producers и consumers разделены. Для показа выбранной части клиентов используйте фильтр Containers: итоговая линия суммирует только выбранные экземпляры, отдельно для каждого сценария.

Для задержек показаны среднее и p50/p75/p95/p99 каждого consumer и линия `COMBINED selected`. Общее среднее взвешено по числу samples; общий перцентиль рассчитан по объединённой гистограмме. Значения перцентилей не складываются. На главном дашборде есть переход к этому представлению с сохранением сценария и диапазона времени.
